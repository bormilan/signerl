# UTF-8 signing and XML export (#49)

## Problem and implementation

xmerl produces Unicode character lists. Canonicalization and export treated these
as byte lists, corrupting Latin-1 characters and raising `badarg` for characters
above U+00FF. An unsupported encoding declaration could also survive signing
while disagreeing with the emitted bytes.

- `signerl_c14n` emits UTF-8 from Unicode characters in both supported modes.
  Binary text and attributes are decoded as UTF-8 before escaping to avoid
  double encoding. Unicode element/attribute names follow the same output path.
- `signerl_xml` validates complete input byte sequences as UTF-8, restricts
  declarations to UTF-8 (or absent encoding), and gives xmerl an explicit UTF-8
  default to prevent auto-detection of UTF-16/32 input. File parsing uses the same
  boundary while retaining its existing whitespace normalization and XML base.
- XML export and text extraction encode Unicode as UTF-8. Direct `export/2`
  rejects an incompatible supplied encoding declaration. Regex constants remain
  in `include/signerl_xml.hrl`.
- README documents encoding, declarations, BOM behavior, and failures; the test
  responsibility map includes the new unit/API/file/independent comparisons.

Public return shapes remain unchanged: unsupported signing declarations return
`invalid_prolog`; parser/verification encoding failures return `invalid_xml`.
Signing still requires a declaration without a BOM; verification still accepts
an absent declaration or UTF-8 BOM. Low-level file parsing raises on invalid input
or missing files rather than accidentally treating `{error, enoent}` as XML.

## Validation and review

Tests were added before implementation. Focused EUnit reproduced 11 failures,
including corrupted canonical bytes, Unicode export failure, and accepted
unsupported declarations. Public API tests reproduced Unicode signing `badarg`
and an accepted unsupported declaration. A further direct-export test reproduced
UTF-8 output incorrectly labelled Latin-1 before adding its guard.

The file regression exposed a pre-existing false positive: the Common Test case
used a missing relative fixture path, and the old parser simplified the file
error into `{error, [], []}`. The test now resolves the real fixture, asserts its
library structure, and separately checks that missing files raise.

Focused validation after implementation passes: 72 XML/C14N EUnit cases and all
69 Common Test cases. The public regression signs the same multilingual fixture
through `sign/3` and `sign/4`, with binary/file inputs; verifies before tampering;
checks preserved parsed text/attributes; then rejects a Unicode content mutation.
Production parsing plus canonicalization matches independent xmllint output for
both C14N 1.1 and Exclusive C14N on that fixture.

Complete native `test`, `as test cover`, `flint`, `dialyzer`, and final `tall`
all pass: 174 EUnit + 69 Common Test = 243 cases, no skips/suite-loading errors,
and 100% coverage across all ten production modules. Formatting and Xref pass;
project Dialyzer analysis has no findings. Fresh PLT construction emits upstream
xmerl missing-spec warnings; no warning suppression was added. `git diff --check`
and local documentation links pass. Review found no unresolved implementation
findings after the export guard and file-control corrections.

Native runtime: installed OTP 28.4.2 and pinned rebar3 3.25.1; CI uses OTP 26/27
and pinned 28.5.0.7 on Ubuntu/Windows. All six jobs on the final PR head must pass
before merge; their logs/results are recorded in the PR validation summary.
No Docker checks are part of the current repository workflow.
